# AI crawler policy, and the one step that is not in this repository

Date: 2026-08-07. Raised by an SEO/GEO audit of the live site.

## The finding

`public/robots.txt` blocked five agents outright: GPTBot, ChatGPT-User, CCBot,
anthropic-ai and Claude-Web. Two of those are not training crawlers.

`ChatGPT-User` and its equivalents are the fetch an assistant makes *because a
person asked it a question*. Blocking them means an assistant asked "what is a
good Persian poetry app" cannot read hamdam.com.au in order to answer, and so
cannot recommend it. For a niche app with a small link profile and a six page
site, that retrieval path is one of the few organic channels available, and it
was closed by a file that was trying to do something else.

The block was written to protect the poetry translations from being absorbed
into training corpora. That aim is correct and is unchanged. The file now
separates the two behaviours instead of treating every AI agent as one thing:

| Purpose | Agents | Policy |
| --- | --- | --- |
| Training corpora | GPTBot, ClaudeBot, anthropic-ai, Claude-Web, CCBot, Applebot-Extended, meta-externalagent, Bytespider | Disallow |
| Search index and user-triggered retrieval | OAI-SearchBot, ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot, Perplexity-User, Applebot | Allow |

Plus a machine-readable `Content-Signal: search=yes, ai-input=yes, ai-train=no`
on the wildcard group, which states the same policy in the form Cloudflare's
Content Signals Policy defines.

### One deliberate exception

`Google-Extended` is allowed, and it does not fit the split above. It is a
single control governing both Gemini grounding and Gemini training, with no
way to separate them. Allowing it accepts training in exchange for being
answerable and citable in Gemini. That trade was taken knowingly because
absence from the answer engines is the larger cost here. To reverse it, move
the `Google-Extended` block into the training section of `robots.txt`. Nothing
else needs to change.

## The step that is not in this repository

**Editing `robots.txt` alone does not unblock anything.**

Cloudflare's managed AI crawler block sits in front of the origin and returns
403 before `robots.txt` is ever requested. While that rule is on, every `Allow`
line added on 2026-08-07 is inert. The audit observed the managed block and the
manual `robots.txt` block operating together on the live site, which is why the
same agents appeared twice.

Someone with dashboard access has to do this part:

1. Cloudflare dashboard, `hamdam.com.au` zone.
2. Security, then Bots, then the AI Scrapers and Crawlers control.
3. Either turn it off, or set it to block training crawlers only, so the
   retrieval agents in the table above reach the origin and are governed by
   `robots.txt` instead.

This repository's rules bar changing Cloudflare or DNS configuration from a
session, so it was not done here.

### Verifying it took effect

From outside the Cloudflare edge, with a user agent that should now be allowed:

```
curl -sSI -A 'Mozilla/5.0 AppleWebKit/537.36 (KHTML, like Gecko); compatible; ChatGPT-User/1.0; +https://openai.com/bot' https://hamdam.com.au/
```

A `200` means the managed rule is no longer intercepting it. A `403` means step
3 has not been done, or has not propagated yet. Repeat with `OAI-SearchBot`,
`Claude-User` and `PerplexityBot`. Also confirm a blocked one still behaves as
intended: `GPTBot` should reach the origin and be refused by `robots.txt`
rather than by the edge, which is the correct outcome, since a `403` at the
edge and a `Disallow` in `robots.txt` are the same result for a compliant
crawler.

## What this does not fix

Retrieval crawlers can now read the site, but there are only six URLs to read,
two of which are Terms and Privacy. Unblocking is what makes the content layer
worth building; it is not a substitute for it. The remaining audit items, in
the order they were prioritised, are the schema enrichment (done in the same
commit as this note), the content cluster of poet and cultural moment pages,
and links.

The content cluster carries a hard constraint that is worth restating here,
because it is the thing most likely to be forgotten under deadline: those pages
may be built only on cited public domain translations (Nicholson, Whinfield,
Bell). `src/data/verses.ts` is generated byte-exact from the iOS verse bank,
which still contains the AI-generated English that FACTS.md marks CONTESTED.
Building content pages on it would put that problem into Google's index
permanently, and unblocking the retrieval crawlers first would put it into the
answer engines too.
