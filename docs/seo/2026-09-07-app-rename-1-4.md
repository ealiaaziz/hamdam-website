# The app is renamed at 1.4, and the site follows the store rather than leading it

Date: 2026-09-07. Ealia: from version 1.4 the App Store listing is called
**Hamdam: Reflection Companion**, not **Hamdam: Daily Persian Poetry**.

## Nothing changed on the live site today, and that is the change

1.4 is not released. Checked, not assumed: `itunes.apple.com/lookup` on
2026-09-07 returned version **1.3.2** under the old name on both the AU and US
storefronts, released 2026-09-01.

This repository has a standing rule that the site must never publish something
the App Store contradicts. It was written for version numbers. It applies
harder to the name, because of where the name appears:

- the English homepage `<title>`;
- `alternateName` on the `SoftwareApplication` node in the JSON-LD;
- the anchor text of the footer's one crawlable link to the listing;
- the slug in the canonical store URL.

Every one of those is a place a crawler lines up what this site says against
what Apple's own page says. Publishing "Hamdam: Reflection Companion" while
Apple still serves "Hamdam: Daily Persian Poetry" would not be an early
announcement. It would be a contradiction, on the four surfaces built to be
compared.

## So the name is derived, not flipped

`src/lib/appName.js` decides the name from the version the store itself
reports, read through the generated record in `src/data/releases.ts`. Below 1.4
it is the old name; from 1.4 it is the new one. Ship the release, run
`node scripts/extract-releases.mjs --write`, and the title, the structured
data, the footer link and the URL slug all change in that same build.

A boolean would have been less code. It would also have been a thing somebody
had to remember on the day they were busy shipping a release, and the cost of
forgetting runs in both directions: flip it early and the site contradicts
Apple, flip it late and the site is stale. Deriving it removes the day and the
person from the problem. The failure direction is deliberate too: an
unreadable or missing version resolves to the **old** name, because being
briefly stale is far cheaper than announcing a name Apple has not applied.

Verified end to end by temporarily setting the record to 1.4 and building:
title, `alternateName`, footer anchor and slug all became the new name
together, `softwareVersion` read 1.4, and the Farsi homepage was untouched.
Restored afterwards; nothing about that experiment is committed.

## The one surface that cannot follow, and the alarm on it

`public/llms.txt` is a static file with no build step, and it carries the
canonical store URL as a literal. A test asserts that literal matches
`APP_STORE_CANONICAL_URL`, so on the day 1.4 is regenerated `npm test` fails
until that one line is updated by hand. That failure is the feature: the
alternative is a rename that half-lands and nobody notices.

## What this costs in search, stated accurately

The old store name carried "Persian Poetry" inside the app name itself. The
new one does not, so on the face of it the rename removes the site's strongest
term from the homepage title. Two things keep that from being the loss it
sounds like.

First, the 1.4 title is **"Hamdam: Reflection Companion, Persian Poetry and
Journal"**, not the name alone. The term moves from the branded half of the
title to the descriptive half. It is still in the title, still on the
homepage, still in the `<h1>` and body copy that were never touched by this.

Second, and this is the part worth reading before anyone panics or celebrates:
the homepage is not where this site earns its impressions. From the 2026-09-03
Search Console reading in `docs/seo/traffic-log.md`, `/` drew **12
impressions** at average position 3.0. The poet pages drew far more:
`/poets/rumi/` 54, `/poets/saadi/` 52, `/poets/hafez/` 50, `/fal-e-hafez/` 31.
The named queries were `ganjoor rumi`, `ganjoor saadi` and `ganjoor khayyam`.
Not one recorded query was "daily persian poetry" or anything like it, and not
one of those pages' titles is affected by this rename.

So the honest expectation is: small, homepage-only, and partly mitigated by
keeping the term in the title. Worth watching in the next reading, not worth
arguing about in advance. If the rename is right for the product, the search
argument does not outweigh it.

## What is not done here

This repository is the website. The rename has to actually happen in App Store
Connect, and the app's own name in `hamdam-ios` is a separate change in a
separate repository. Nothing here can do either, and nothing here should be
read as evidence that either has been done.

After 1.4 goes live:

1. `node scripts/extract-releases.mjs --write`
2. `npm run check:release`, which fetches the store and fails if the repo and
   Apple disagree
3. `npm test`, which will fail on `public/llms.txt` until its store URL is
   updated to the new slug
4. after deploy, confirm the live page agrees with Apple:

```
curl -sS https://hamdam.com.au/ | grep -o '<title>[^<]*</title>'
curl -sS 'https://itunes.apple.com/lookup?id=6784461990&country=au' | grep -o '"trackName":"[^"]*"'
```
