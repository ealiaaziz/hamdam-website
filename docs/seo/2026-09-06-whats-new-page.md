# The What's New page, 2026-09-06

`/whats-new/` and `/fa/whats-new/`, plus a version number in the structured
data on all four of those and the two homepages.

## Why it was asked for, and what it actually does

The request was: "Google and app directories show version 1.1 or 1.2 while we
are on 1.3, build a What's New page so they catch up."

**Half of that premise does not hold, and it is worth being blunt about it
before anyone measures this page against the wrong expectation.**

- A page on `hamdam.com.au` has no effect on what the App Store product page
  says. Apple's listing was already correct: the live version on the day this
  was built is **1.3.2**, released 1 September 2026, not 1.3.
- It has no effect on third party app directories either. They scrape
  `itunes.apple.com/lookup`, which also already says 1.3.2, and they refresh on
  their own schedule. Nothing published here reaches them.
- Where a stale version appears inside a Google result **for the App Store
  listing**, that is Google's cache of Apple's page. Only Apple's page can fix
  it.

What the page does do, and these are real:

1. **It gives this domain a URL that answers "which version is Hamdam on".**
   There was none. Every description of the app on the open web was free to sit
   on whatever version it first saw, and nothing we controlled contradicted it.
2. **It puts the answer where an answer engine can cite it.** Static HTML, no
   script needed to render the text, `softwareVersion` in JSON-LD on six pages,
   the page named in `llms.txt` with an explicit instruction not to quote a
   version from an app directory. That is the surface ChatGPT, Perplexity and
   AI Overviews actually read, and it is the surface where the stale numbers
   were showing up.
3. **It is the one page on this site with a reason to change every few weeks.**
   Everything else here is evergreen. A page that updates on a real event, is
   linked site wide from the footer, and carries `dateModified`, is a crawl
   invitation the rest of the site does not offer.
4. **It is a landing page for release announcements** that is ours rather than
   Apple's, in both languages, which the App Store cannot be because it has no
   Persian storefront.

What it will not do is move a head term. It ranks, if it ranks at all, for
`hamdam update`, `hamdam release notes`, `hamdam 1.3.2` and the like: brand
plus modifier, tiny volume, and worth having only because it costs nothing to
keep. **Nobody should read a flat US impression count next month as this page
failing.** The US work is elsewhere and is named at the bottom of this file.

## What is on the page

**Feature releases only. Ealia's call, 2026-09-06.** The page tells the story of
1.3 and 1.2. Point releases on top of them (1.3.1, 1.3.2) are not listed, on the
grounds that a reader arriving here wants to know what the app can do now, and a
widget refresh fix is noise at that altitude even when its notes are well
written.

**No version number is visible on the page except the feature releases.** A chip
above the heading named the live release (1.3.2) for about an hour on the day
this was built, and Ealia had it removed: it put 1.3.2 above a first card
reading 1.3, and that is a reader's puzzle rather than a reader's answer.

The live version is still published, in `softwareVersion` in the structured data
on all four pages that carry it. That is the half that has to stay, and the two
halves do different jobs:

| | what it says | why |
| --- | --- | --- |
| `softwareVersion` (JSON-LD) | the live release, point release included | machine readable, must never disagree with the store |
| `<title>`, meta description | the newest feature release | this is what should be indexed |
| the cards | feature releases only | the story a reader came for |

So a human reads 1.3 and a crawler reads both. The English lead paragraph says
point releases are not listed, which is what keeps the visible 1.3 an editorial
choice rather than a stale number; a reader who checks the App Store, sees
1.3.2, and comes back here has been told why it is not on the page. The Farsi
page cannot say it, for the reason in the next section.

**The filter is applied at render, never to the record.** `src/data/releases.ts`
keeps every release it has text for, including 1.3.2; `featureReleases()` in
`src/lib/releases.js` filters for display. That is what keeps
`npm run check:release` meaningful: it compares the newest entry in the record
against the live store, and it could not do that against a filtered record. A
test asserts the record is larger than the rendered list, so quietly filtering
the data instead would fail loudly.

`src/data/releases.ts` is generated by `scripts/extract-releases.mjs` from two
sources and nothing else:

- the **live listing** via `itunes.apple.com/lookup`, which is authoritative for
  whatever version is current and is the only source that cannot be stale;
- `docs/app-store/v*-whats-new.md` in **hamdam-ios**, which is the record for
  releases Apple no longer publishes notes for.

An independent second witness that the 1.3 text is what actually shipped, since
it comes from a markdown file rather than from Apple: every Farsi fragment in
`src/data/siteCopy.ts`'s Garden block, which was split out of the **live** 1.3
listing on 2026-08-27 by a different route on a different day, appears verbatim
inside the generated 1.3 entry. A test asserts it.

## What is missing, and why it is missing rather than invented

**1.0 and 1.1 are feature releases and are not on the page.** Their notes were
never written into hamdam-ios, and Apple publishes only the current version's
notes, so there is no source a script or a session can read. The same is true of
1.0.1, 1.1.1 and 1.3.1, though those are point releases and would not have been
listed anyway.

So the page carries two entries where it could carry four. That was the
deliberate trade: writing plausible release notes for a release nobody has the
text of is exactly the failure mode this repository's rules exist to prevent.

**To close it, and this is the highest value thing Ealia can do for this page:**
open App Store Connect, read the `whatsNew` field for 1.1 and for 1.0, and add
each to `ARCHIVED` in `scripts/extract-releases.mjs` with a markdown file in
hamdam-ios, or paste the entry into `src/data/releases.ts` following the shape
the generator emits. The Farsi half comes with it, because the field is
bilingual; nothing is translated.

## The Farsi page is deliberately thinner

No Persian is authored in this repository, so the Farsi page carries:

- the heading, byte exact from the app's own What's New sheet
  (`Localization.swift`, `whatsNewTitle`);
- the version label, byte exact from the app's Settings row
  (`settingsVersionRowShort`), with Persian numerals as the app renders them;
- the release notes, which are Ealia's own published text;
- poet and moment names, which already exist in both languages.

It omits the lead paragraph, the "Earlier versions" heading and the "More about
Hamdam" heading, because no approved Farsi exists for any of them. That is the
same asymmetry the moment and poet pages already carry and it is confined to
chrome: every word of release copy is there in both languages.

**For Ealia, if he wants to close it:** three short Persian lines would do it,
an introduction of one or two sentences and two section labels. Nothing else on
the page needs him.

## The release checklist, from now on

Every time a version ships:

```
node scripts/extract-releases.mjs --write   # pulls the live listing
git diff src/data/releases.ts               # read it before committing
npm run check:release                       # fails if the site and store disagree
npm test && npm run check:persian && node scripts/check-dashes.mjs
```

`npm run check:release` is the piece that matters and is new. The site now
publishes a version number, and a published version number goes stale on its
own. This repository has a documented history of exactly that: `CLAUDE.md` in
hamdam-ios sat four builds behind the project file twice, and `CLAUDE.md` here
has been wrong about deploys three times. The number is never typed anywhere;
it is read from the generated record, and that command reads the store and says
which side is behind.

It is not in the pre-commit hook, because it needs the network and a hook that
fails offline is a hook people disable.

## What would actually move US visibility

Recorded here so this page is not mistaken for the answer to that question.

The 2026-09-03 Search Console reading is the evidence, and it says the site
owns `ganjoor <poet>` at positions 4 to 6 and is invisible at 43 to 64 for
`hafez`, `saadi poems` and every other head term. Nothing about release notes
changes either fact. `HANDOFF-2026-09-03-seo.md` items 1 to 3 are still the
work: the Yalda page before December, titles and descriptions on the pages
already ranking, and a decision recorded either way on the head terms.

One thing this page does contribute to that: it is the first page here to state
the current version in machine readable form, and `sameAs`, `softwareVersion`
and a consistent `@id` are entity signals that compound over months. That is an
argument for having built it now rather than in December, not an argument that
it will show up in a fortnight.
