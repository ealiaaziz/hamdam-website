## The five rules that cost the most when broken

1. **Never author, translate or hand-edit Persian.** `npm run check:persian`
   validates the Unicode range, not the grammar, so it will pass wrong Persian
   happily. If a Farsi string must change and no approved replacement exists in
   the repo or the app, the only safe edit is *deletion of the false part*,
   using words already present. Anything else waits for Ealia or Sima.
2. **Pushing `main` deploys. Pushing any other branch does not.** This line has
   been wrong in `CLAUDE.md` three times, so verify rather than trust:
   ```bash
   curl -sS https://hamdam.com.au/ | grep -o '/_astro/BaseLayout\.[A-Za-z0-9_-]*\.css'
   ls dist/_astro/BaseLayout.*.css
   ```
   Same hash means it deployed. Deploys observed this session took 60 to 90 seconds.
3. **`scripts/predeploy-check.mjs` guards `npm run deploy` only.** The Workers
   Builds path never runs it, so a push to `main` publishes whatever is committed.
   Run it by hand before pushing anything substantial.
4. **`FACTS.md` is the claim gate, and it is editable, which makes it dangerous.**
   It once offered a false claim as its own ALLOWED example, and five published
   strings inherited it. When correcting a claim, fix `FACTS.md` first, then the
   code, then the pinned test.
5. **Verify facts about the app against `hamdam-ios`, not against this repo's
   comments.** A code comment here asserted a presentation claim was "true today".
   It was not, and nobody had checked.

## Open items

### 1. The App Store listing carries a screenshot of a screen the app cannot display

**The most consequential open item, and it is outside this repo.**

Confirmed still true on 2026-08-21. The 1.2 listing's screenshots are:

```
01-hero-en.png  07-faal-en.png  03-wisdom-en.png  02-reflect-en.png
05-journey-en.png  04-roots-en.png  06-privacy-en.png
```

`01-hero-en.png` is **screenshot number one** and is synthetic. It comes from
`TodayScreenshotView` in `hamdam-ios`
(`Hamdam/Hamdam/DebugTools/ScreenshotOrchestrator/ScreenshotViewFactory.swift:355-423`),
a `#if DEBUG` composition that never calls `TodayView`. Its verse card
(`:406-422`) has **no language check**, so it stacks Persian over English in
both locales. Four of its six elements are absent from production Today: the
Persian couplet in EN mode, both languages together, the streak pill (removed
2026-07-23), and the Apple Health row (a different tab).

It is a **regression**: the 1.1.1 listing used genuine device captures
(`Today.png`, `Root.png`, `امروز.png`). 1.2 swapped them for the composed set,
so the store page got less accurate as the app got more so.

**Fix is in App Store Connect.** No route from here: no ASC credentials, no
`.p8` key, no `fastlane`/`altool`, no MCP or Composio toolkit for ASC (checked;
Composio has none and proposed scraping the public page instead). Screenshots
are frozen on a released version, so this needs a new editable version.

Also worth fixing in the same pass: `03-wisdom`'s burned-in caption promises
"Wisdom from five masters ... Hafez, Rumi, Saadi, Khayyam and Parvin Etesami"
over a Discover screen showing no poet and no verse.

`07-faal-en.png` is new in 1.2, appears genuine, and is the screen *immediately
before* the one state that could honestly show a verse (the revealed Hafez
Faal). Capturing that revealed state is the obvious candidate for both the
listing and a future site hero.

Full record: `FACTS.md`, "the hero screenshot" entry.

### 2. The Farsi homepage no longer mentions that English exists

`src/pages/fa/index.astro` previously said the verse arrives «در کنار برگردان
انگلیسی» (beside the English translation). That is false: the app shows one
language at a time, and in Farsi mode deliberately shows no English at all.
The clause was **deleted**, on Ealia's instruction, using only words already in
the approved sentence.

The English page says "in its original Persian, or in English". The Farsi one
now says less. Restoring parity needs roughly five words of Persian from Ealia
or Sima.

**Do not machine-author it.** The whole app repo was searched for an approved
string meaning "in Persian or in English". None exists. The closest match is the
v1.0 App Store listing draft, which contains the *false* wording; the next
closest sits in a file whose own note says it is "authored by Claude and
byte-validated, not reviewed by Sima", which is the same provenance class as
writing it fresh.

### 3. `/fal-e-hafez/` looks like it improved, and the sample is too small to say

Position 9, against 27.1 in the previous window. That is what the headings were
for. **But its impressions fell from 14 to 4 while the position improved**, and
a page ranking better on far fewer impressions is not obviously winning.

The test is whether impressions recover to the earlier volume while the position
holds. Do not credit the headings until they do.

### 4. The legal pages outrank everything, and the standing explanation is wrong

`/privacy/` at position 5 and `/fa/privacy/` at 8.3 are the best-ranking pages
on the site, and produced the only click in the 16 to 18 Aug window. The
2026-08-16 log entry dismissed this as "an artefact of having nothing else
indexed". Eleven pages are indexed now and the legal pages still beat all of
them, so that explanation is wrong or incomplete. Nobody has investigated.

This may be the site's only genuine ranking signal. Worth understanding.

### 5. The upstream cause, in `hamdam-ios`

`ScreenshotViewFactory.swift:29-31` asserts its previews are "assembled entirely
from real, shared production components ... never a hand-drawn mock". True of the
components, false of the arrangement, and nothing flags the difference. That
sentence is why a synthetic screenshot survived three weeks on the homepage and
then shipped to the App Store.

Fixing it means correcting the comment and ideally making the harness render the
real view. That is a PR against the app repo and was **not authorised** in this
session.

## Traps that cost time this session

| Trap | What happens | Guard |
| --- | --- | --- |
| **Composio `time_info` is unreliable** | Reported the date two days early on 17 Aug; a whole report was written against the wrong date | `date -u`, cross-check `curl -sS -I https://apps.apple.com/ \| grep -i '^date:'` |
| **`grep -c` on minified HTML** | Counts matching *lines*, not occurrences. Reported 1 h2 where there were 3 | `grep -o '<h2' file \| wc -l` |
| **GSC `data_state`** | `final` lags 2 to 3 days; `all` adds provisional days Google later revises. Check `firstIncompleteDate` in the response | Run both, label provisional figures |
| **GSC query breakdown understates totals** | Withheld queries are omitted. Only 10 of 42 impressions were named in the last window | Take headline numbers from `dimensions: []` |
| **The GitHub MCP read path rewrites HTML** | Injects `rel="nofollow noreferrer noopener" target="_blank"` into every `<a>` in a PR body. Looked like a real defect in our own PR | Verify against the rendered page or the source file |
| **Storefront agreement is not proof** | Three storefronts agreed on a stale version one day, then disagreed with each other the next, mid-propagation | Sample repeatedly; weight the rendered product page, which flushes first |
| **Trigger connectors** | `connectors` on `create_trigger` is disabled for this org, so a fresh-session routine has no Composio and cannot reach GSC | Bind the routine to an existing session, or create it from the claude.ai Routines UI |
